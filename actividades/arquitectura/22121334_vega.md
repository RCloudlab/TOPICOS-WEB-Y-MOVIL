## 1. Clasificar la plataforma actual (15)

Así está mi plataforma (`plataforma-entregas`), la que corre con un solo `Dockerfile`:

```
 Navegador
   │  GET  /entregas/            → Django le entrega recomendar.html
   │  POST /entregas/recomendar/ → JSON del paquete + "modelo"
   ▼
┌──────────────────────── 1 contenedor (python:3.12-slim) ────────────────────────┐
│  Django  (manage.py runserver 0.0.0.0:8000)                                     │
│                                                                                 │
│   urls.py ─► views.recomendar ─► recomendador.py ─► modelo/*.joblib (en RAM)    │
│                     │                  └─► reglas.es_posible()                  │
│                     └─► medios.crear_medio(...).planear()                       │
│                                                                                 │
│   db.sqlite3 (archivo dentro del mismo contenedor)                              │
└─────────────────────────────────────────────────────────────────────────────────┘
```

- **Cliente:** el navegador con la página `recomendar.html`, que Django mismo sirve.
- **Proceso del servidor:** uno solo, Django. Adentro viven la vista, el recomendador, las reglas, los medios y los tres modelos cargados en memoria.
- **URL que usa el front:** `POST /entregas/recomendar/`, que responde JSON (`medio`, `motivo`, `ranking`, `descartados`, `plan`).

En la versión de clase con `docker-compose` (nginx + `web` ×3 + Postgres) cambia el despliegue, pero no la clasificación: las tres copias `web` son la misma imagen con todo adentro.

**Clasificación:** es un **monolito con API**. La evidencia: `views.recomendar` llama a `obtener_recomendador()` y a `crear_medio()` con un `import` de Python dentro del mismo proceso. No existe ninguna llamada de red entre partes del servidor; la única red es la del navegador hacia Django.

## 2. "Ya tenemos endpoints, entonces son microservicios" (20)

**Lo refuto.** Tener `/entregas/recomendar/` y `/entregas/hola/` significa que el **cliente** quedó separado del servidor: el navegador o una app solo conocen el contrato JSON y no el código. Pero microservicios es separar **los servidores entre sí**. Aquí el recomendador no tiene su propio proceso, ni su propio despliegue, ni su propia base. Si cambio `reglas.py` tengo que reconstruir y reiniciar todo Django, y si el modelo de 50 MB tumba la memoria, se cae también el formulario. Muchos endpoints sobre un mismo proceso siguen siendo un monolito, solo que bien expuesto.

## 3. El caso de las 3:00 en los dos mundos (25)

El paquete de prueba (`paquete.json`): 12.64 km, 0.31 kg, periferia, despejado, **hora_salida = 3**. Lo corrí en mi plataforma con los tres modelos:

| Modelo | Lo que prefiere el modelo | ¿Reglas corrigieron? | Medio final |
|---|---|---|---|
| árbol | dron 84.1%, moto 13.1% | Sí: dron descartado por las reglas del negocio | **moto** (confianza 13%) |
| bosque | moto 81% | No | moto |
| red | moto 98.3% | No | moto |

### Hoy (monolito): todo es `import` y llamadas en memoria

```
views.recomendar(request)
  └─ json.loads + validar CAMPOS                       (views.py)
  └─ obtener_recomendador("arbol")                     (recomendador.py)
       └─ RecomendadorSklearn.explicar(paquete)
            └─ self._modelo.predict_proba(df)          (joblib ya en RAM)
            └─ reglas.es_posible(medio, paquete)       (reglas.py) → dron imposible a las 3:00
  └─ crear_medio("moto").planear(paquete)              (medios.py)
  └─ JsonResponse(...)
```

Son llamadas a funciones dentro del mismo proceso: microsegundos, sin red, y no pueden fallar "a medias". Si el `.joblib` no existe, `obtener_recomendador` lanza `FileNotFoundError` y la vista responde 503.

### Si el recomendador fuera otro servicio

```
Navegador ─HTTP─► Pedidos (Django) ─HTTP POST /sugerir─► Recomendar (Flask/FastAPI + .joblib + reglas)
                         ▲                                         │
                         └──────────────── JSON ◄──────────────────┘
```

- Hay **dos saltos de red** en lugar de uno: navegador → Pedidos y Pedidos → Recomendar.
- En vez de `from .recomendador import obtener_recomendador`, Pedidos hace `requests.post(RECOMENDAR_URL + "/sugerir", json=paquete, timeout=2)`.
- **Si Recomendar no contesta**, el `import` ya no existe para salvarnos. Pedidos tiene que decidir: esperar como máximo el timeout y luego (a) responder un error claro ("recomendación no disponible, intenta más tarde"), o (b) usar un respaldo local con solo reglas (por ejemplo `elegir_medio(km, kg)` sin modelo) y marcar en la respuesta que no vino del modelo. Lo que **no** debe hacer es quedarse colgado ni crear un pedido con un medio inventado.
- Las reglas (`es_posible`) se tienen que ir **con** el modelo a Recomendar. Si se quedan en Pedidos, el dron de las 3:00 viajaría por la red y alguien más tendría que acordarse de descartarlo.

| | `import` (hoy) | HTTP (separado) |
|---|---|---|
| Tiempo | microsegundos | milisegundos + red |
| Fallas posibles | excepción de Python | timeout, conexión rechazada, 500, JSON mal formado |
| Contrato | firma de la función | JSON versionado entre servicios |
| Desplegar el modelo nuevo | reconstruir todo Django | reconstruir solo Recomendar |

## 4. Decisión de la empresa (20)

El Random Forest pesa ~50 MB (mi `modelo_bosque.joblib` mide 51.4 MB) y se reentrena cada semana; los pedidos casi no cambian.

**Mi postura: sacar solo el servicio de IA (recomendar) y dejar lo demás como monolito con API.**

1. **Ritmos de cambio distintos.** El modelo cambia cada semana y los pedidos casi nunca. Hoy, cada reentrenamiento obliga a reconstruir y reiniciar Django completo, con el riesgo de romper pedidos que nadie tocó. Separado, solo se redespliega Recomendar.
2. **Memoria y réplicas.** Con 3 réplicas `web` y, por ejemplo, 2 workers de gunicorn en cada una, el bosque se carga 6 veces: ~300 MB solo de modelo para atender también peticiones que ni lo usan (ver un pedido, el formulario). Un servicio aparte carga el modelo en las réplicas que yo decida.
3. **Falla aislada.** Si el modelo nuevo viene mal (versión de scikit-learn distinta, archivo corrupto), hoy se cae Django completo. Separado, Pedidos sigue registrando y consultando pedidos con un respaldo de reglas.

No separo todo porque usuarios, pedidos y seguimiento comparten base y transacciones (`atomic` para pedido + cobro). Partirlos agregaría consistencia distribuida sin ningún beneficio, si casi no cambian.

## 5. Un microservicio propuesto (20)

**Servicio `recomendar`.**

- **Qué se va:** `recomendador.py`, `reglas.py`, la carpeta `modelo/` con los `.joblib` y scikit-learn en su `requirements.txt`. Expone `GET /salud` y `POST /sugerir` (recibe el paquete y regresa `medio`, `confianza`, `ranking`, `descartados`, `corregido_por_reglas`). No crea folios ni toca la base.
- **Qué se queda en Django:** las vistas, los modelos `Pedido`/`Cobro`, la base, `transaction.atomic`, `on_commit`, la idempotencia, y `medios.py` (`crear_medio(...).planear()`), porque planear la entrega es parte del pedido, no de la predicción. Django deja de tener scikit-learn y lee `RECOMENDAR_URL` de una variable de entorno.
- **Por qué ese corte:** es la única parte que cambia a otro ritmo, la más pesada en memoria y la que tiene una dependencia delicada (versión exacta de scikit-learn para leer el `.joblib`). Además ya tiene una frontera limpia en el código: la vista solo llama `obtener_recomendador(...).explicar(paquete)`. Convertir esa llamada en un `POST` es reemplazar un `import` por un cliente HTTP con timeout y respaldo, sin rediseñar lo demás.
